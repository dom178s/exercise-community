## 5. 既知の問題

### 応答だけ失われた場合に二重登録される可能性
**コードからの推定**

Supabase側で保存が成功したにもかかわらず通信切断などで応答だけが失われた場合、利用者が再送すると同じ報告が2件保存される可能性があります。報告ごとのID（`client_id`）と一意制約で防ぐ案を Issue #4 で扱います。

### 履歴表示で入力内容をHTMLとして表示している
**確認済み**

`showReportHistory()` と `showCheerHistory()` は入力内容を `innerHTML` で表示しています。他の利用者の報告をSupabaseから読み込んで表示する前に、`textContent` 等へ置き換える必要があります（Issue #5）。

### データが端末・環境ごとに分かれる
**確認済み / コードからの推定**

主要データをlocalStorageに保存しているため、異なるブラウザやオリジンでは同じデータを共有できません。複数ユーザー・複数端末での利用には中央保存とユーザー識別が必要です。

## 8. セキュリティ・運用上の確認事項

### Supabaseキー
**確認済み**

フロントエンドにはブラウザ向けpublishable keyが含まれています。

secret/service-role keyをフロントエンドや公開リポジトリへ追加しないことをルールとします。

### RLS
**確認済み（2026-11-02、Issue #2）**

`public.reports` はRLS有効。`anon` に対して `INSERT WITH CHECK (true)` と `SELECT USING (true)` が設定されています。

**要対応**

現在のアプリはSupabaseから読み込みを行っていないため、`SELECT` ポリシーは不要です。ブラウザ用キーは公開されているため、このままでは誰でも全件を読み取れます。ユーザー名などを保存する前に `SELECT` ポリシーを外し、入力値の範囲をCHECK制約で制限します。

### 個人情報
**要確認**

一般公開へ進む場合は、収集する情報、保存期間、アクセス権限、利用規約・プライバシー関連の対応などを整理する必要があります。
