# Architecture

## 1. この文書について
**確認済み**

この文書は、運動コミュニティMVPの現在のシステム構成とデータの流れを整理するものです。実装から確認できない内容は推測で確定せず、「コードからの推定」または「要確認」として記載します。

## 2. システム概要
**確認済み**

現在のアプリは、HTML・CSS・JavaScriptで構成された静的Webアプリです。

- `index.html`: 画面と入力フォーム
- `style.css`: レイアウト・見た目
- `script.js`: アプリの処理、localStorageへの保存、Supabase REST APIへの運動報告送信
- GitHub Pages: Webアプリの公開
- localStorage: 主要なユーザーデータの端末内保存
- Supabase: 運動報告のサーバー側保存を試作中

## 3. 現在の構成
**確認済み**

```text
利用者
  ↓
Webブラウザ / LINE MINI Appのエンドポイント
  ↓
GitHub Pagesで配信された静的Webアプリ
  ├─ index.html
  ├─ style.css
  └─ script.js
       ├─ localStorage
       │    ├─ ポイント
       │    ├─ 連続記録
       │    ├─ 運動履歴
       │    ├─ 応援履歴
       │    └─ 所持ステッカー
       │
       └─ Supabase REST API
            └─ reports（運動報告の保存を試作中）
```

## 4. 主なデータフロー

### 運動報告
**確認済み**

1. 利用者が日付・運動内容・時間・気分・コメントを入力する。
2. `showReport()` が入力内容を取得する。
3. 必須項目を確認する。
4. `reportData` を作成する。
5. `saveReportToSupabase(reportData)` を呼び出す。
6. 同じ報告をlocalStorage上の運動履歴にも保存する。
7. 連続記録とポイントを更新する。
8. 当日の報告ボタンを無効化する。

**要確認**

Supabaseへの保存に失敗した場合でも、その結果を待たずにlocalStorage側の保存・ポイント付与などが進む現在の実装になっています。そのため、画面上では成功したように見えてもSupabaseには保存されていない状態が発生し得ます。

### 応援
**確認済み**

応援メッセージまたは所持ステッカーを使って応援できます。応援履歴と1日の応援回数はlocalStorageへ保存され、ポイント付与は1日2回までです。

### ステッカー
**確認済み**

ポイントを消費してステッカーを購入し、所持ステッカーをlocalStorageに保存します。購入済みステッカーは重複購入できません。所持ステッカーは応援にも利用できます。

### 運動プラン
**確認済み**

負荷「小・中・大」を選ぶと、`suggestPlan()` がJavaScript内に定義された固定の運動プランを表示します。現在は外部AIサービスを呼び出していません。

## 5. データ保存

### localStorage
**確認済み**

現在確認できる保存キーは次のとおりです。

- `points`
- `streak`
- `pointHistory`
- `reports`
- `cheers`
- `cheerCount`
- `lastCheerDate`
- `lastReportDate`
- `ownedStickers`

localStorageはブラウザ・オリジン単位の保存であり、現在の実装では複数利用者の中央管理にはなっていません。

### Supabase
**確認済み / 要確認**

`script.js` からSupabase REST APIの `reports` エンドポイントへPOSTする処理があります。

現在アプリ側で送信している主なキーは `date`, `exercise`, `time`, `mood`, `comment` です。

Supabase側の実際のテーブル定義、必須列、型、RLSポリシーとの整合性は改めて確認が必要です。運動報告が正常保存されないケースが確認されているため、原因を確定してから修正します。

## 6. 外部サービス

### GitHub / GitHub Pages
**確認済み**

ソースコードをGitHubで管理し、GitHub Pagesを利用してWebアプリを公開しています。

### Supabase
**確認済み**

運動報告の中央保存先として導入を進めています。ブラウザ向けpublishable keyをフロントエンドから利用しています。

**要確認**

一般公開前にRLS・ユーザー認証・ユーザー単位のデータアクセス設計を確認する必要があります。secret/service-role keyはフロントエンドへ配置しません。

### LINE MINI App
**コードからの推定 / 要確認**

現在の3ファイル内にはLIFF SDKの読み込みや `liff.init()` などのLINE固有処理は確認できません。現状はGitHub PagesのWebアプリをLINE MINI Appのエンドポイントとして表示している構成と考えられます。LINEユーザー識別を利用する場合は別途設計・実装確認が必要です。

## 7. 認証・ユーザー識別
**要確認**

現在のコードにはログイン・認証・ユーザーIDに基づくデータ分離の実装は確認できません。

少人数MVPから利用者を増やす前に、誰の運動報告・ポイント・応援なのかを安全に識別する方法を決める必要があります。

## 8. ビルド・テスト・デプロイ

### ビルド
**確認済み**

現状はビルド工程のない静的Webアプリです。

### テスト
**確認済み**

自動テストコードは現在のリポジトリには確認できません。ブラウザでの手動確認が中心です。

### デプロイ
**確認済み**

GitHub Pagesによるデプロイを利用しています。

**要確認**

GitHub Pagesの詳細なデプロイ設定・ブランチ設定、およびCIとして追加すべき検証内容は今後整理します。

## 9. 現時点の主な設計課題
**確認済み / 要確認**

- localStorageとSupabaseの責務分担
- Supabase保存失敗時のエラー処理
- Supabaseのテーブル定義と送信データの整合
- RLSとアクセス権限
- ユーザー認証・識別
- 少人数MVPから一般公開へ拡張する際のデータ設計
- 自動テスト・静的解析・CIの導入要否
- 課金を行う場合の決済・権限管理
- 本物のAI運動提案を導入する場合の構成と安全性

## 10. 設計方針
**要確認**

当面は少人数でMVPを安定して検証できることを優先しつつ、後から不特定多数へ展開する際に全面的な作り直しにならないよう、ユーザー識別・データ保存・セキュリティの境界を段階的に整理します。
